## [Unreleased]

### Додано

- Інфраструктура репозиторію: CI на GitHub Actions (лінт, перевірка типів і
  тести для обох пакетів), шаблони issue та pull request, `CODEOWNERS`.
- ESLint для серверного пакета — раніше лінт існував тільки для фронтенду.
- Документація: `CLAUDE.md`, `CONTRIBUTING.md`, `DESIGN.md`, `docs/API.md`,
  цей журнал, README для `server/`.
- `.editorconfig` і налаштування VS Code (`.vscode/`), включно з конфігураціями
  дебагу сервера та тестів.
- Скрипти `lint`, `typecheck` і `test` у корені, що проганяють обидва пакети.
- Розгортання одним контейнером: `Dockerfile` (тристадійна збірка),
  `.dockerignore` і `render.yaml` для Render. Клієнт і API віддаються з одного
  origin, тому cookie лишаються першосторонніми, CORS не задіяний, а власний
  домен не потрібен.
- Express віддає зібраний клієнт: статика з річним кешем (імена файлів містять
  хеш) і SPA-фолбек для клієнтських маршрутів, з окремим винятком для кореня
  `/` і підтримкою `HEAD` — обидва потрібні для коректних health-check'ів.
  Монтуються лише тоді, коли збірка клієнта справді присутня, тож розробка
  через Vite не змінюється.
- `GET /healthz` — перевіряє ще й з'єднання з MongoDB.

### Змінено

- **Ламка зміна контракту.** Стан дня в `dailyCompletions` тепер enum
  `pending | done | failed` замість булевого `completed`. Тіло
  `PATCH /habits/:id/complete` — `{ status, date? }` замість
  `{ completed, date? }`. Причина: булеве значення не могло виразити «я цього не
  зробив» — і воно, і «день ще не настав» були `false`, тож червона позначка,
  яку ставив користувач, жила лише в локальному стані компонента і зникала при
  першому ж перезапиті чи перезавантаженні. Стан «прострочено» свідомо не
  зберігається: він виводиться з дати (`pending` + день у минулому), бо
  зберігання вимагало б процесу, що опівночі в часовому поясі кожного
  користувача переписує рядки.
  **Перед розгортанням треба один раз виконати**
  `npm --prefix server run migrate:day-status` — скрипт ідемпотентний і
  переносить `true → done`, решту → `pending` (ніколи не `failed`: намір за
  старим `false` відновити неможливо).
- Явна позначка «не виконано» тепер обриває серію. Поблажливість «ряд може
  закінчуватися вчора» лишається, але стосується тільки дня, щодо якого рішення
  ще не ухвалене; `failed` — це вже ухвалене рішення. `calculateStreak`
  переписано на прохід назад від сьогодні: попередня версія збирала множину
  виконаних дат і не могла побачити ні пропущеного дня, ні явної відмови.
- Перевірка «дата початку не в минулому» дістала допуск в один день: локальний
  календарний день клієнта може відставати від UTC-дня сервера, і користувач у
  UTC−5 увечері не міг створити звичку на власне сьогодні.
- `npm test` у фронтенді тепер `vitest run` замість watch-режиму — інакше він
  ніколи не завершується в CI. Для інтерактивного режиму додано `test:watch`.
- Переписано кореневий `README.md` і `frontend/README.md` (останній був
  незміненим boilerplate від `create-vite`).
- `VITE_API_URL` за замовчуванням порожній — це означає «той самий origin».
  Раніше незадана змінна давала літерал `undefined` перед кожним шляхом.

### Виправлено

- День, який показує щоденний екран, більше не розходиться з днем, який він
  запитує в API. Клієнт слав повний ISO-момент: локальна північ, пропущена
  через `toISOString()`, — це попередній день за UTC скрізь на схід від
  Гринвіча. Наслідки бачив користувач: звичка, створена сьогодні, зникала при
  поверненні на сьогоднішню клітинку і поверталася після F5; сусідні дні
  показували один спільний стан, бо клітинка «завтра» приносила й відмічала
  запис «сьогодні»; вибір сьогоднішньої дати у формі створення відхилявся як
  «дата в минулому». Тепер день їде на дріт як `YYYY-MM-DD` через
  `frontend/src/lib/dates.ts`, а мітки з сервера читаються UTC-акцесорами.
- Позначка «не виконано» на сьогодні переживає перезавантаження. Раніше сервер
  не мав де її зберегти, тож вона трималася в локальному стані `HabitCard` — і
  зникала при кожному перезапиті дня.
- Сторінка статистики більше не покладається на випадковість: `markHabitCompletion`
  оновлює і `habitsForDate`, і `habits`. Раніше правильні цифри там трималися
  лише на тому, що сторінка перезапитує все при монтуванні.
- Звичка на сьогодні більше не позначається як провалена на захід від UTC.
  `HabitCard` читав північ UTC локальними геттерами, тож при UTC−5 кожен
  невідмічений день ставав «минулим» на добу раніше.
- Гість більше не отримує двох помилок у консолі при відкритті сторінки.
  `App` питав `GET /auth/me`, отримував закономірний 401, після чого клієнт
  автоматично пробував `POST /auth/refresh` — оновити сесію, якої не існувало.
  Браузер пише кожну 4xx у консоль, тож обидві були червоними. Тепер клієнт
  спершу дивиться на `csrf_token` (єдина читабельна для JS cookie, з тим самим
  строком життя, що й refresh-токен): немає її — немає сесії, і жоден із двох
  запитів не робиться.
- CSP більше не блокує емодзі. `react-apple-emojis` вантажить зображення з
  `em-content.zobj.net`, а дефолтний `img-src` у helmet — це `'self' data:`.
  Поки клієнт віддавав Vite, це не проявлялося; щойно його почав віддавати
  Express, усі емодзі зникли б без жодної помилки на сервері.
- Спроба розгорнути клієнт і сервер як два окремі сервіси на Render (кожен на
  своєму `*.onrender.com`) ламала вхід: `403 FORBIDDEN` на
  `POST /auth/refresh`. `onrender.com` — публічний суфікс (Public Suffix
  List), тому CSRF-cookie, видана API-сервісом, недосяжна для JS клієнтського
  сервісу. Це не помилка конфігурації, а структурна несумісність double-submit
  CSRF з розділеними origin без спільного власного домену — звідси рішення
  віддавати обидва з одного процесу.

## [0.3.0] — 2026-07-30

Великий рефакторинг архітектури та безпеки. Публічний контракт API змінився:
кожна відповідь тепер приходить у спільному конверті.

### Додано

- Шар сервісів (`server/src/services/`) між контролерами й моделями. Перевірка
  власника винесена туди, тож «користувач A не дістане звичку користувача B» —
  властивість шару, а не те, що треба пам'ятати в кожному ендпоінті.
- Валідація кожного запиту через Zod: схеми в `server/src/validation/` є єдиним
  джерелом правди, а типи DTO виводяться з них через `z.infer`.
- Middleware `validate`, що перевіряє `body`, `params` і `query`, повертає
  одразу всі проблеми, згруповані за полем, і коерсить `body` та `params`.
- Захист від CSRF за схемою double-submit: cookie `csrf_token`, що читається
  скриптом, і заголовок `X-CSRF-Token`, який клієнт має повторити.
- Ротація refresh-токенів: поля `tokenVersion` і `refreshSessions` у моделі
  користувача дозволяють завершити конкретну сесію або всі одразу.
- Мемоїзовані селектори (`createSelector`) для похідних значень у сторі.

### Змінено

- **Ламає сумісність:** усі відповіді загорнуто в конверт
  `{ success, data }` / `{ success, error: { code, message, details? } }`.
  Клієнтський `apiRequest` розгортає його, тож виклики отримують дані напряму.
- **Ламає сумісність:** сесія переїхала з токена в тілі відповіді у httpOnly
  cookie. Токени більше недоступні для JavaScript, тому XSS не може їх забрати.
  Refresh-cookie обмежена шляхом `/auth`.
- Обробка помилок централізована: хендлери кидають `AppError` і нічого не
  ловлять, Express 5 сам передає це в єдиний обробник.
- Три типи звичок згорнуто в один (`build` / `quit`) — попередній поділ
  дублював логіку без різниці в поведінці.
- Списки на фронтенді більше не перемальовуються цілком при зміні одного
  елемента; усунуто дублювання компонентів.

### Виправлено

- Два дефекти, які виявилися при винесенні шару сервісів (обробка дат поза
  межами розкладу звички та підрахунок серії).
- Паралельні запити на оновлення сесії більше не змагаються між собою: клієнт
  тримає один спільний `refreshInFlight`, інакше переможений лишався б із уже
  витраченим токеном.

### Безпека

- Токени сесії недосяжні для JavaScript (httpOnly).
- Зміна пароля завершує всі інші сесії користувача.
- Окремі ключі підпису для access- і refresh-токенів; у production обидва
  обов'язкові, поза ним є fallback на `JWT_SECRET` із попередженням у лозі.

## [0.2.0] — 2026-07-25

Об'єднання двох репозиторіїв в один і приведення бекенду до робочого стану.

### Додано

- Монорепо: історію `FocusPath_server` влито у спільний репозиторій,
  `npm run dev` піднімає фронтенд і сервер разом через `concurrently`.
- Пакет спільних типів `shared/` — тільки `.d.ts`, тому жодна зі сторін не
  отримує ні кроку збірки, ні рантайм-залежності.
- Спільний кореневий `.env` для обох пакетів і скрипт `seed:admin`.
- Відновлено серверний тест-сьют: Jest + supertest + `mongodb-memory-server`,
  база піднімається в пам'яті на кожен прогін.
- Структуроване логування через `pino` / `pino-http`.

### Безпека

- `helmet`, налаштований CORS зі списком дозволених origin, обмеження розміру
  тіла запиту.
- Обмеження частоти запитів: загальне (300 / 15 хв), для входу й реєстрації
  (10 / 15 хв, успішні спроби не рахуються) та окреме для AI-генерації.
- Захист від NoSQL-ін'єкцій: `sanitizeFilter` у mongoose плюс сувора перевірка
  типів у схемах.
- Пароль зберігається з `select: false`, обмежений за довжиною в байтах
  (bcrypt мовчки відкидає все після 72 байтів), кількість раундів налаштовна.

## [0.1.0] — 2026-05-13

Перша функціональна версія застосунку.

### Додано

- Реєстрація, вхід і перевірка токена; захищені маршрути на клієнті.
- Звички: створення, редагування, видалення, розклад на весь період,
  відмітка виконання по днях, кроки всередині звички, підрахунок серії.
- Генерація плану звички через OpenAI з анімацією очікування.
- Сторінка статистики зі зведенням і розбивкою по звичках.
- Профіль: редагування даних, зміна пароля, аватар, видалення акаунта.
- Адаптивний інтерфейс: тижневий та місячний вибір дати, свайпи для навігації
  тижнями, анімації переходів (`framer-motion`), сітка карток звичок.
- Тести компонентів і сторів на Vitest + Testing Library.
- Перехід зі SCSS-модулів на централізований CSS і Tailwind.
