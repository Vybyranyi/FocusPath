## Як це реалізовано

Усе, що описано вище, зроблено без змін напряму. Те, що специфікація лишала на
розсуд або що довелося уточнити:

- **`PUT /journal/:day` замінює, а не зливає.** Поле, якого немає в тілі,
  прибирається — так людина забирає настрій назад; порожнє тіло видаляє запис,
  тому порожнього запису в базі немає. Відповідь — `{ entry }`, де `entry` буває
  `null`.
- **«Не в майбутньому» з добою запасу** — як і дата старту звички: людина на схід
  від Гринвіча вже живе завтрашнім днем, коли сервер ще ні. Так само для нотатки.
- **Причина зникає, коли день перестає бути `failed`, будь-яким шляхом**, а не
  лише відміткою: змінили ліміт `quit`, скоротили програму, зсунули правило.
  Перевірка стоїть у `settle`, де й так перераховується все похідне.
  `reasonPrompted` лишається: день, про який уже питали, не питають вдруге, навіть
  якщо його зняли й знову позначили.
- **`reasonPrompted` без причини — теж непорожній запис.** Інакше «питали,
  відмовились» губилось би разом із порожнім записом, а питання поверталось би.
- **Закриття вікна «Чому?» без відповіді рахується пропуском** і записує
  `reasonPrompted: true`; інакше Escape означав би «спитайте ще раз».
- **Нотатку можна лишити на будь-якому дні, який у звички є в розкладі**, зокрема
  на вихідному чи паузі: «хворів, проспав» — саме той контекст, що робить серію
  зрозумілою.
- **Налаштування змінюється окремим шляхом** (`preferences.askFailureReason` як
  dotted-ключ), а не заміною всього об'єкта: наступне налаштування — те ж коучеве
  `coachReadsNotes` — не повинно стирати це.
- **Картка дня зберігає себе** після 0,8 с без змін, а при виході з дня шле те,
  що ще не пішло. Показується лише для дня, що настав, і лише коли прийшла
  відповідь саме для цього дня.
- **Історія** — місяць назад, ще двічі по місяцю (до 90 днів: у межах 92, які
  читає сервер за раз).

## Суть і навіщо

Звички без контексту — лише відмітки. Щоденник додає дві речі:

- **запис дня**: настрій, енергія й кілька слів про день загалом;
- **контекст звички-дня**: нотатка до виконання й причина зриву.

Разом вони дають відповідь на питання, яке людина сама не бачить: як звички
пов'язані з самопочуттям і чому саме вона зривається. Це й сировина для
коуча в третьому PR.

## Модель даних

### Нова колекція `JournalEntry`

| Поле | Тип | Примітки |
| --- | --- | --- |
| `userId` | ObjectId, required | |
| `day` | Date, required | північ UTC |
| `mood` | Number 1–5, optional | |
| `energy` | Number 1–5, optional | |
| `text` | String, до 2000 символів, optional | |

Індекс `{ userId: 1, day: 1 }` **унікальний**. Запис, у якому не лишилось
жодного поля, видаляється. `toJSON` зрізає `userId` і `__v`.

### `HabitDay` — нові поля

| Поле | Тип | Примітки |
| --- | --- | --- |
| `note` | String, до 280 символів, optional | нотатка до виконання |
| `failureReason` | `{ code: ReasonCode, text?: String до 200 }`, optional | лише для дня зі станом `failed` |
| `reasonPrompted` | Boolean | панель причини вже показувалась для цього дня — більше не питати (Q21) |

```
ReasonCode = 'no_time' | 'forgot' | 'no_energy' | 'ill'
           | 'circumstances' | 'didnt_want' | 'other'
```

Тип — у `shared/`, перелік значень — на сервері поруч із моделлю, на
клієнті — `Record<ReasonCode, string>` з підписами, щоб пропущений код був
помилкою типів.

Якщо день перестає бути `failed` (людина змінила відмітку), `failureReason`
прибирається: причина зриву дня, якого більше не було, бреше статистиці.

### `User` — нові поля

| Поле | Тип | Примітки |
| --- | --- | --- |
| `preferences.askFailureReason` | Boolean, default `true` | Q21 |

Змінюється через `PATCH /auth/profile` — поле додається в білий список
схеми.

## Контракт API

| Ендпоінт | Призначення |
| --- | --- |
| `PUT /journal/:day` | `{ mood?, energy?, text? }` — створити або оновити запис дня; `:day` — `YYYY-MM-DD`, не в майбутньому |
| `DELETE /journal/:day` | прибрати запис |
| `GET /journal?from&to` | записи за проміжок, не більше 92 днів; для історії в Activity |
| `PATCH /habits/:id/days/:day/note` | `{ note }`; порожній рядок прибирає нотатку |
| `PATCH /habits/:id/days/:day/reason` | `{ code, text? }` або `{ skipped: true }`; лише для дня зі станом `failed` |

`:day` у шляху — ключ дня. Він перевіряється тією ж функцією, що й у тілі
запитів, і проходить через `startOfUtcDay`, а не через `new Date()` у
локальному поясі.

`GET /habits/daily` додає до `day` поля `note` і `failureReason`, а у
відповідь — `journal` для запитаного дня, щоб денний екран не робив другий
запит.

Ендпоінти щоденника скоуплені за власником так само, як звички: у сервісі,
а чужий запис — `NOT_FOUND`.

## Клієнт

- **Картка дня** внизу денного екрана для вибраного дня: настрій — п'ять
  облич, енергія — п'ять рівнів, текст розгортається на тап. Зберігається
  без кнопки, із затримкою після введення; стан «збережено» видно поруч.
  Для майбутнього дня картки немає.
- **Нотатка до звички-дня** — у картці звички, під станом дня.
- **Панель причини** з'являється після `failed` (свайп чи кнопка): сім
  варіантів, поле для тексту, «Пропустити» й «Не питати більше». Пропуск
  записує `reasonPrompted: true`.
- **Історія** в Activity: дні з настроєм і енергією, від нових до старих,
  з відкриттям запису.
- **Налаштування** в профілі: «Питати причину, коли я не виконав звичку».

## Приватність

- Щоденник ніколи не потрапляє в план при публікації в Explore.
- `GET /auth/export` отримує `journal` і нотатки та причини в днях.
- `DELETE /auth/account` видаляє `JournalEntry` і `HabitDay` користувача
  повністю.
- Що з цього бачить AI — [`AI_COACH.md`](AI_COACH.md#що-йде-в-ai).

## Тести

Сервер: створення, оновлення й видалення запису дня; заборона майбутнього;
унікальність запису на день; причина лише для `failed` і зникає, коли день
перестає бути `failed`; скоупінг власника; експорт і видалення акаунта.

Клієнт: картка дня зберігає без кнопки; панель причини з'являється один раз
і не з'являється з вимкненим налаштуванням; майбутній день без картки.
