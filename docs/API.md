## Конверт відповіді

Кожен ендпоінт відповідає в одній із двох форм.

**Успіх**

```json
{
  "success": true,
  "data": { }
}
```

**Помилка**

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Validation failed",
    "details": {
      "email": ["Must be a valid email address"],
      "password": ["Password must be at least 8 characters long"]
    }
  }
}
```

`details` присутнє лише тоді, коли є розбір по полях. Ключі — шляхи до полів,
включно з вкладеними: `steps.0.title`.

Клієнтський `apiRequest` розгортає конверт, тому виклики отримують вміст `data`
напряму, а будь-яка невдача приходить як `ApiError`.

## Автентифікація

Сесія живе в cookie. Токенів у тілі відповіді немає взагалі.

| Cookie | httpOnly | Path | Час життя |
| --- | --- | --- | --- |
| `access_token` | так | `/` | 15 хвилин |
| `refresh_token` | так | `/auth` | 7 днів |
| `csrf_token` | ні | `/` | 7 днів |

Усі запити з браузера мають іти з `credentials: 'include'`, інакше cookie не
надсилаються і будь-який захищений ендпоінт відповість `401`.

Коли `access_token` спливає, захищений виклик повертає `401`. Правильна реакція
— один раз викликати `POST /auth/refresh` і повторити запит; клієнтський
`apiRequest` робить це автоматично. Refresh-токен **ротується при кожному
використанні**: старий одразу перестає бути дійсним, тож двох одночасних
оновлень бути не повинно.

## CSRF

Для методів, що змінюють стан (`POST`, `PATCH`, `PUT`, `DELETE`), треба
надіслати заголовок:

```
X-CSRF-Token: <значення cookie csrf_token>
```

- `GET`, `HEAD` і `OPTIONS` перевірку не проходять — їм вона не потрібна.
- Запити, у яких немає жодної сесійної cookie, теж пропускаються. Саме це
  звільняє вхід і реєстрацію без списку винятків.
- Розбіжність або відсутність токена — `403 FORBIDDEN`.

## Коди помилок

| Код | HTTP | Коли трапляється |
| --- | --- | --- |
| `VALIDATION_ERROR` | 400 | Тіло, параметри або query не пройшли схему. Є `details` |
| `BAD_REQUEST` | 400 | Дата поза межами розкладу, невірний поточний пароль, нечитабельний JSON |
| `UNAUTHORIZED` | 401 | Немає сесійної cookie, недійсний підпис токена, невірні дані входу |
| `TOKEN_EXPIRED` | 401 | Токен прострочений — треба викликати `/auth/refresh` |
| `FORBIDDEN` | 403 | CSRF-токен відсутній або не збігається |
| `NOT_FOUND` | 404 | Ресурс не існує **або** належить іншому користувачу |
| `CONFLICT` | 409 | Email уже зайнятий |
| `PAYLOAD_TOO_LARGE` | 413 | Тіло запиту більше за 2 МБ |
| `RATE_LIMITED` | 429 | Перевищено ліміт запитів |
| `SERVICE_UNAVAILABLE` | 503 | Зовнішній сервіс (OpenAI) недоступний |
| `INTERNAL_ERROR` | 500 | Непередбачена помилка. Деталі лишаються в лозі, клієнту не віддаються |

`NOT_FOUND` замість `FORBIDDEN` для чужих ресурсів — навмисно: інакше відповідь
підтверджувала б, що об'єкт із таким id існує.

## Обмеження частоти

| Ліміт | Вікно | Максимум | Ключ |
| --- | --- | --- | --- |
| Загальний | 15 хв | 300 запитів | IP |
| Автентифікація (`/auth/register`, `/auth/login`) | 15 хв | 10 запитів | IP |
| AI-генерація (`POST /habits/ai`) | 60 хв | 5 запитів | userId (IP як запасний варіант) |

Успішні спроби входу **не рахуються** до ліміту автентифікації, тому легітимний
користувач його не відчуває, а перебір паролів обмежений десятьма промахами.

AI-ліміт рахується по користувачу, а не по адресі: спільна офісна мережа не має
з'їдати чужу квоту, а зміна адреси — множити свою.

Під `NODE_ENV=test` лімітери вимкнені.

## CORS

Дозволені origin беруться з `CORS_ORIGIN` (список через кому). За замовчуванням
— `http://localhost:5173`. Запити без заголовка `Origin` (curl, health-check)
не обмежуються. Відмова відбувається через ненадсилання CORS-заголовків, а не
через помилку 500.

## Службові ендпоінти

### `GET /healthz`

Те, що опитує хостинг, аби вирішити, чи піднявся деплой.

**Авторизація:** не потрібна · **Ліміт:** не рахується

Приймає `GET` і `HEAD` (health-checkeри часто шлють саме `HEAD`), з будь-яким
`Accept`-заголовком чи без нього. Змонтований перед логером і лімітером:
платформа опитує його щокілька секунд, і ні рядок у лозі, ні витрачена квота
запитів на кожен опит не потрібні.

**`200`** → `{ "status": "ok" }`

**`503`** → `SERVICE_UNAVAILABLE`, якщо процес слухає, але з'єднання з MongoDB
не готове. Такий інстанс віддавав би самі 500, тож у ротацію він не потрапляє.

## Ендпоінти `/auth`

### `POST /auth/register`

Створює користувача і одразу видає сесію.

**Авторизація:** не потрібна · **Ліміт:** автентифікація

**Тіло**

| Поле | Тип | Правила |
| --- | --- | --- |
| `name` | string | обрізається, 1–50 символів |
| `surname` | string | обрізається, 1–50 символів |
| `birthday` | string \| Date | будь-яка дата, що розбирається |
| `gender` | `"male"` \| `"female"` | — |
| `email` | string | обрізається, потім перевіряється формат |
| `password` | string | ≥ 8 символів і ≤ 72 байтів |

**`201`** → `{ "user": User }` плюс три cookie сесії.

**Помилки:** `VALIDATION_ERROR`, `CONFLICT` (email зайнятий), `RATE_LIMITED`.

---

### `POST /auth/login`

**Авторизація:** не потрібна · **Ліміт:** автентифікація (успішні спроби не рахуються)

**Тіло:** `{ "email": string, "password": string }`

Формат email тут **не** перевіряється суворо: наявний акаунт має отримати
«невірні дані», а не зауваження про адресу.

**`200`** → `{ "user": User }` плюс cookie сесії.

**Помилки:** `VALIDATION_ERROR` (порожні поля), `UNAUTHORIZED` (невірні дані),
`RATE_LIMITED`.

---

### `POST /auth/refresh`

Обмінює refresh-cookie на нову сесію. Тіла немає — токен читається з cookie.

**`200`** → `{ "user": User }` плюс три нові cookie.

Старий `sessionId` замінюється новим, тож попередній refresh-токен більше
недійсний.

**Помилки:** `UNAUTHORIZED` (немає cookie, токен витрачений, `tokenVersion`
змінився після зміни пароля), `TOKEN_EXPIRED`.

---

### `POST /auth/logout`

Видаляє поточну сесію зі списку прийнятих і чистить cookie. Нечитабельний токен
не вважається помилкою — відкликати нема чого, а cookie все одно очищаються.

**`200`** → `{ "data": null }`

---

### `GET /auth/me`

**Авторизація:** обов'язкова

**`200`** → `{ "user": User }`

Клієнт викликає це на старті замість зберігати сесію локально. Для гостя `401`
— нормальний шлях, а не збій.

---

### `PATCH /auth/profile`

**Авторизація:** обов'язкова

**Тіло** — будь-яка непорожня підмножина: `name`, `surname`, `birthday`,
`gender`, `email`, `avatar`.

`avatar` — base64 data URI. Приймаються лише `image/png`, `image/jpeg` і
`image/webp`, розмір до 1 МБ.

**`200`** → `{ "user": User }`

**Помилки:** `VALIDATION_ERROR` (у тому числі «жодного поля не передано»),
`CONFLICT` (email зайнятий іншим користувачем), `NOT_FOUND`.

---

### `PATCH /auth/password`

**Авторизація:** обов'язкова

**Тіло:** `{ "currentPassword": string, "newPassword": string }`

Зміна пароля **завершує всі інші сесії** на всіх пристроях: `tokenVersion`
зростає, `refreshSessions` очищається. Той, хто змінює пароль, одразу отримує
нову сесію, тож із поточного пристрою не вилітає.

**`200`** → `{ "data": null }` плюс нові cookie.

**Помилки:** `BAD_REQUEST` (поточний пароль невірний), `VALIDATION_ERROR`.

---

### `DELETE /auth/account`

**Авторизація:** обов'язкова

**Тіло:** `{ "password": string }` — підтвердження паролем, щоб викрадена сесія
не могла видалити акаунт.

Видаляє користувача **і всі його звички**.

**`200`** → `{ "data": null }`

**Помилки:** `BAD_REQUEST` (пароль невірний).

## Ендпоінти `/habits`

Усі потребують авторизації. Усі операції скоуплені за власником: чужа звичка
повертає `NOT_FOUND`.

### `POST /habits`

Створює звичку вручну і одразу генерує розклад на весь період.

**Тіло**

| Поле | Тип | Правила |
| --- | --- | --- |
| `title` | string | 1–100 символів |
| `description` | string? | до 500 символів |
| `category` | string? | до 50 символів |
| `steps` | array? | `[{ title: string, completed?: boolean }]` |
| `startDate` | string \| Date | **не в минулому** (порівняння по днях у UTC) |
| `duration` | number | ціле, 1–365 |
| `type` | `"build"` \| `"quit"` | — |
| `color` | string | непорожній |
| `icon` | string | непорожній |

**`201`** → `{ "habit": Habit }`

---

### `POST /habits/ai`

Те саме, але план генерує OpenAI.

**Ліміт:** 5 запитів на годину, по користувачу

**Тіло:** `title`, `startDate`, `type`, `color`, `icon` — як вище, плюс
`duration` **необов'язковий**: відсутнє, `null` або `0` означають «нехай модель
сама обере тривалість».

**`201`** → `{ "habit": Habit, "aiGenerated": true }`

**Помилки:** `SERVICE_UNAVAILABLE` (OpenAI недоступний), `RATE_LIMITED`.

---

### `GET /habits/daily`

Головний ендпоінт щоденного екрана.

**Query:** `date` — необов'язкова, за замовчуванням сьогодні.

Повертає лише звички, чинні на цю дату (початок ≤ дата ≤ останній день плану).
Замість повного розкладу кожна звичка несе `dayInfo` — запис саме цього дня — і
`completedCount` за весь період. Тому показ одного дня не тягне за собою решту.

**`200`**

```json
{
  "date": "2026-07-31T00:00:00.000Z",
  "habits": [
    {
      "_id": "...",
      "title": "Ранкова пробіжка",
      "description": "",
      "category": "",
      "steps": [],
      "startDate": "2026-07-01T00:00:00.000Z",
      "duration": 30,
      "type": "build",
      "color": "#4F8DF9",
      "icon": "🏃",
      "currentStreak": 5,
      "isCompleted": false,
      "dayInfo": {
        "_id": "...",
        "dayTitle": "День 31",
        "date": "2026-07-31T00:00:00.000Z",
        "status": "pending"
      },
      "completedCount": 18
    }
  ]
}
```

---

### `GET /habits`

Усі звички користувача повністю, з розкладом, найновіші першими.

**`200`** → `{ "habits": Habit[] }`

---

### `GET /habits/:id`

**`200`** → `{ "habit": Habit }` · **Помилки:** `VALIDATION_ERROR` (id не є
ObjectId), `NOT_FOUND`.

---

### `PUT /habits/:id`

**Тіло** — непорожня підмножина полів створення. Правило «не в минулому» тут
**не діє**: наявна звичка цілком законно могла початися раніше.

Зміна `startDate` або `duration` перебудовує розклад. Записи переносяться **за
позицією в плані, а не за датою**: третій день лишається третім. Скорочення
тривалості відкидає зайві дні, збільшення — додає порожні.

**`200`** → `{ "habit": Habit }`

---

### `DELETE /habits/:id`

**`200`** → `{ "habitId": string }`

---

### `PATCH /habits/:id/day`

Перейменовує конкретний день розкладу.

**Тіло:** `{ "date": string | Date, "dayTitle": string }` (`dayTitle` — 1–200
символів)

**`200`** → `{ "habit": Habit }`

**Помилки:** `BAD_REQUEST` — дата поза межами тривалості або відсутня в
розкладі.

---

### `PATCH /habits/:id/complete`

Виставляє статус дня. Перераховує `currentStreak` і `isCompleted`.

**Тіло:** `{ "status": "pending" | "done" | "failed", "date"?: string }` — без
`date` береться сьогодні.

`failed` — це «я цього не зробив», сказане користувачем, і воно обриває серію.
`pending` повертає день у невідмічений стан. Стану «прострочено» тут немає: він
випливає з дати (`pending` + день у минулому) і не зберігається — інакше
знадобився б процес, що опівночі в часовому поясі кожного користувача
переписує рядки.

**`200`** → `{ "habit": Habit }`

**Помилки:** `BAD_REQUEST` — дата поза межами розкладу.

---

### `PATCH /habits/:id/steps/:stepId`

Перемикає стан кроку всередині звички.

**`200`** → `{ "stepId": string, "completed": boolean, "habit": Habit }`

**Помилки:** `VALIDATION_ERROR` (некоректний id), `NOT_FOUND` (немає такої
звички або кроку).

## Форми даних

Канонічні визначення — у [`shared/src/`](../shared/src), звідти їх імпортують
обидва пакети.

### `User`

```ts
{
  _id: string;
  name: string;
  surname: string;
  birthday: string;   // ISO 8601
  gender: "male" | "female";
  email: string;
  avatar?: string;    // data URI, поки користувач не вибрав — відсутній
  createdAt: string;
  updatedAt: string;
}
```

`password`, `tokenVersion` і `refreshSessions` не потрапляють у відповідь
ніколи — їх зрізає `toJSON` у моделі.

### `Habit`

```ts
{
  _id: string;
  title: string;
  description?: string;
  category?: string;
  steps?: { _id: string; title: string; completed: boolean }[];
  startDate: string;  // ISO 8601, північ UTC
  duration: number;   // завжди дорівнює dailyCompletions.length
  type: "build" | "quit";
  color: string;
  icon: string;
  currentStreak: number;
  isCompleted: boolean;
  dailyCompletions: {
    _id: string;
    dayTitle: string;
    date: string;     // ISO 8601, північ UTC
    status: "pending" | "done" | "failed";
  }[];
  createdAt: string;
  updatedAt: string;
}
```

### `HabitSummary`

Те, що повертає `GET /habits/daily`: усе з `Habit`, крім `dailyCompletions`,
`createdAt` і `updatedAt`, плюс `dayInfo` (запис одного дня) і `completedCount`.

### Дати

Усі дати нормалізовані до **півночі UTC**. Інакше «сьогодні» залежало б від
часового поясу процесу і той самий день міг би збігатися або не збігатися
залежно від того, де запущено сервер.

**Клієнт надсилає день як `YYYY-MM-DD`, а не як повний ISO-момент.** Календарний
день — це локальний день користувача, той, що написаний на клітинці, яку він
натиснув. Локальна північ, пропущена через `toISOString()`, — це попередній день
за UTC скрізь на схід від Гринвіча, тож повний момент означав інший день, ніж
той, що на екрані. Голий ключ дня однозначний: сервер парсить його як північ
UTC, що збігається з тим, як зберігається розклад.

У зворотний бік мітки з відповіді — це вже північ UTC, і читати їх треба
UTC-акцесорами. Локальні геттери зсувають їх на добу на захід від Гринвіча.

Перевірка «дата не в минулому» при створенні має допуск в один день: локальний
день клієнта може відставати від UTC-дня сервера (користувач у UTC−5 о 20:00 ще
на 7-му, коли сервер уже на 8-му).
