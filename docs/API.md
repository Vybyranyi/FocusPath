## Конверт відповіді

Кожен ендпоінт відповідає в одній із двох форм.

**Успіх**

```json
{
  "success": true,
  "data": { }
}
```

**Помилка**

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Validation failed",
    "details": {
      "email": ["Must be a valid email address"],
      "password": ["Password must be at least 8 characters long"]
    }
  }
}
```

`details` присутнє лише тоді, коли є розбір по полях. Ключі — шляхи до полів,
включно з вкладеними: `steps.0.title`.

Клієнтський `apiRequest` розгортає конверт, тому виклики отримують вміст `data`
напряму, а будь-яка невдача приходить як `ApiError`.

## Автентифікація

Сесія живе в cookie. Токенів у тілі відповіді немає взагалі.

| Cookie | httpOnly | Path | Час життя |
| --- | --- | --- | --- |
| `access_token` | так | `/` | 15 хвилин |
| `refresh_token` | так | `/auth` | 7 днів |
| `csrf_token` | ні | `/` | 7 днів |

Усі запити з браузера мають іти з `credentials: 'include'`, інакше cookie не
надсилаються і будь-який захищений ендпоінт відповість `401`.

Коли `access_token` спливає, захищений виклик повертає `401`. Правильна реакція
— один раз викликати `POST /auth/refresh` і повторити запит; клієнтський
`apiRequest` робить це автоматично. Refresh-токен **ротується при кожному
використанні**: старий одразу перестає бути дійсним, тож двох одночасних
оновлень бути не повинно.

## CSRF

Для методів, що змінюють стан (`POST`, `PATCH`, `PUT`, `DELETE`), треба
надіслати заголовок:

```
X-CSRF-Token: <значення CSRF-cookie>
```

- `GET`, `HEAD` і `OPTIONS` перевірку не проходять — їм вона не потрібна.
- Запити, у яких немає жодної сесійної cookie, теж пропускаються. Саме це
  звільняє вхід і реєстрацію без списку винятків.
- Розбіжність або відсутність токена — `403 FORBIDDEN`.

**Назва cookie залежить від оточення.** У продакшені вона видається як
`__Host-csrf_token`: префікс `__Host-` означає, що cookie може встановити лише
цей самий хост, лише через HTTPS, лише з `Path=/` і без `Domain` — саме це не
дає сусідньому субдомену перезаписати значення, з яким порівнюється заголовок.
Префікс потребує `Secure`, тому локально (HTTP) назва лишається `csrf_token`, і
він неможливий у деплої з `COOKIE_DOMAIN`, де cookie шариться між двома хостами.

Стара назва `csrf_token` **приймається й далі**, інакше кожна вже видана сесія
залишилася б без виходу: браузер із однією старою cookie не пройшов би перевірку
навіть на `/auth/refresh` і `/auth/logout`. Сесії переходять на префікс під час
наступного оновлення; `/auth/logout` чистить обидві назви. Клієнт читає
`__Host-csrf_token`, а якщо її немає — `csrf_token`.

## Коди помилок

| Код | HTTP | Коли трапляється |
| --- | --- | --- |
| `VALIDATION_ERROR` | 400 | Тіло, параметри або query не пройшли схему. Є `details` |
| `BAD_REQUEST` | 400 | День поза розкладом, у паузі чи на вихідному; пауза чи вихідний у минулому; невірний поточний пароль; нечитабельний JSON |
| `UNAUTHORIZED` | 401 | Немає сесійної cookie, недійсний підпис токена, невірні дані входу |
| `TOKEN_EXPIRED` | 401 | Токен прострочений — треба викликати `/auth/refresh` |
| `FORBIDDEN` | 403 | CSRF-токен відсутній або не збігається |
| `NOT_FOUND` | 404 | Ресурс не існує **або** належить іншому користувачу |
| `CONTENT_REJECTED` | 400 | Модерація відхилила план. `message` — пояснення для автора |
| `CONFLICT` | 409 | Email уже зайнятий; звичку вже опубліковано; план уже взято й ще не пройдено |
| `PAYLOAD_TOO_LARGE` | 413 | Тіло запиту більше за 2 МБ |
| `RATE_LIMITED` | 429 | Перевищено ліміт запитів |
| `SERVICE_UNAVAILABLE` | 503 | Зовнішній сервіс (OpenAI) недоступний |
| `INTERNAL_ERROR` | 500 | Непередбачена помилка. Деталі лишаються в лозі, клієнту не віддаються |

`NOT_FOUND` замість `FORBIDDEN` для чужих ресурсів — навмисно: інакше відповідь
підтверджувала б, що об'єкт із таким id існує.

## Обмеження частоти

| Ліміт | Вікно | Максимум | Ключ |
| --- | --- | --- | --- |
| Загальний | 15 хв | 300 запитів | IP |
| Автентифікація (`/auth/register`, `/auth/login`) | 15 хв | 10 запитів | IP |
| Запит на скидання пароля (`POST /auth/forgot-password`) | 60 хв | 5 запитів | IP; рахуються всі, бо відповідь завжди успішна |
| AI-генерація (`POST /habits/ai`) | 60 хв | 5 запитів | userId (IP як запасний варіант) |
| Публікація плану (`POST /plans`) | 24 год | 5 запитів | userId (IP як запасний варіант) |
| Коуч (`/coach/*`) | 60 хв | 30 запитів | userId (IP як запасний варіант). Лише стеля для зациклених клієнтів: справжній ліміт — унікальність картки за період |

Успішні спроби входу **не рахуються** до ліміту автентифікації, тому легітимний
користувач його не відчуває, а перебір паролів обмежений десятьма промахами.

AI-ліміт рахується по користувачу, а не по адресі: спільна офісна мережа не має
з'їдати чужу квоту, а зміна адреси — множити свою. Ліміт публікацій — з тієї ж
причини плюс одна власна: публікувати може будь-хто й одразу, тож іншого
природного обмежувача в неї немає.

Під `NODE_ENV=test` лімітери вимкнені.

## CORS

Дозволені origin беруться з `CORS_ORIGIN` (список через кому). За замовчуванням
— `http://localhost:5173`. Запити без заголовка `Origin` (curl, health-check)
не обмежуються. Відмова відбувається через ненадсилання CORS-заголовків, а не
через помилку 500.

## Службові ендпоінти

### `GET /healthz`

Те, що опитує хостинг, аби вирішити, чи піднявся деплой.

**Авторизація:** не потрібна · **Ліміт:** не рахується

Приймає `GET` і `HEAD` (health-checkeри часто шлють саме `HEAD`), з будь-яким
`Accept`-заголовком чи без нього. Змонтований перед логером і лімітером:
платформа опитує його щокілька секунд, і ні рядок у лозі, ні витрачена квота
запитів на кожен опит не потрібні.

**`200`** → `{ "status": "ok" }`

**`503`** → `SERVICE_UNAVAILABLE`, якщо процес слухає, але з'єднання з MongoDB
не готове. Такий інстанс віддавав би самі 500, тож у ротацію він не потрапляє.

## Ендпоінти `/auth`

### `POST /auth/register`

Створює користувача і одразу видає сесію.

**Авторизація:** не потрібна · **Ліміт:** автентифікація

**Тіло**

| Поле | Тип | Правила |
| --- | --- | --- |
| `name` | string | обрізається, 1–50 символів |
| `surname` | string | обрізається, 1–50 символів |
| `birthday` | string \| Date | будь-яка дата, що розбирається |
| `gender` | `"male"` \| `"female"` | — |
| `email` | string | обрізається, зводиться до нижнього регістру, потім перевіряється формат |
| `password` | string | ≥ 8 символів і ≤ 72 байтів |

**`201`** → `{ "user": User }` плюс три cookie сесії.

Адреса зберігається в нижньому регістрі. Домен і на практиці скриньки
регістронезалежні, тож `Ann@example.com` і `ann@example.com` — одна адреса;
збереження «як написали» робило з них два акаунти, до яких унікальному індексу
не було чого заперечити, і давало змогу зайняти регістровий варіант уже
використаної адреси. Тому регістровий варіант наявної адреси — `CONFLICT`.

**Помилки:** `VALIDATION_ERROR`, `CONFLICT` (email зайнятий), `RATE_LIMITED`.

---

### `POST /auth/login`

**Авторизація:** не потрібна · **Ліміт:** автентифікація (успішні спроби не рахуються)

**Тіло:** `{ "email": string, "password": string }`

Формат email тут **не** перевіряється суворо: наявний акаунт має отримати
«невірні дані», а не зауваження про адресу. Регістр зводиться до нижнього, як і
при реєстрації, інакше збережену адресу не знайшов би той, хто набрав її з
великої літери.

**`200`** → `{ "user": User }` плюс cookie сесії.

Невідома адреса і невірний пароль дають **однакову** відповідь —
`401 UNAUTHORIZED`, `Invalid email or password` — і однаковий час відповіді:
пароль звіряється навіть тоді, коли акаунта немає, проти хеша, якому нічого не
відповідає. Різниця в будь-якому з двох була б відповіддю на питання «чи є тут
акаунт на цю адресу?» для будь-якої адреси.

**Помилки:** `VALIDATION_ERROR` (порожні поля), `UNAUTHORIZED` (невірні дані),
`RATE_LIMITED`.

---

### `POST /auth/refresh`

Обмінює refresh-cookie на нову сесію. Тіла немає — токен читається з cookie.

**`200`** → `{ "user": User }` плюс три нові cookie.

Старий `sessionId` замінюється новим, тож попередній refresh-токен більше
недійсний.

**Помилки:** `UNAUTHORIZED` (немає cookie, токен витрачений, `tokenVersion`
змінився після зміни пароля), `TOKEN_EXPIRED`.

---

### `POST /auth/logout`

Видаляє поточну сесію зі списку прийнятих і чистить cookie. Нечитабельний токен
не вважається помилкою — відкликати нема чого, а cookie все одно очищаються.

**`200`** → `{ "data": null }`

---

### `GET /auth/me`

**Авторизація:** обов'язкова

**`200`** → `{ "user": User }`

Клієнт викликає це на старті замість зберігати сесію локально. Для гостя `401`
— нормальний шлях, а не збій.

---

### `PATCH /auth/profile`

**Авторизація:** обов'язкова

**Тіло** — будь-яка непорожня підмножина: `name`, `surname`, `birthday`,
`gender`, `email`, `avatar`, `preferences`, плюс необов'язковий
`currentPassword`. `preferences` — `{ askFailureReason?: boolean, coachLanguage?: string,
coachReadsNotes?: boolean }` (мова — два літери, ISO 639-1): змінюється лише
переслане, кожне налаштування окремим шляхом, тож наступне не замінить це.

`avatar` — base64 data URI. Приймаються лише `image/png`, `image/jpeg` і
`image/webp`, розмір до 1 МБ.

**Зміна адреси потребує `currentPassword`.** Те саме правило, що вже діє для
`/auth/password` і `/auth/account`: самої сесії не досить для того, що потрібно
зловмиснику, а адреса — це те, чим акаунт відомий, і через неї пройде будь-який
майбутній шлях відновлення доступу.

Пароль потрібен лише тоді, коли адреса **справді** змінюється: форма профілю
надсилає всі поля, які знає, тож адреса приходить і при перейменуванні, і при
завантаженні аватара, і вимагати пароль за самою її наявністю означало б
вимагати його при кожному редагуванні. Порівняння регістронезалежне.
`currentPassword` не вважається зміною сам по собі — тіло лише з ним отримає
`VALIDATION_ERROR`.

**`200`** → `{ "user": User }`

**Помилки:** `VALIDATION_ERROR` (у тому числі «жодного поля не передано» і
«потрібен поточний пароль» — з `details.currentPassword`), `BAD_REQUEST`
(поточний пароль невірний), `CONFLICT` (email зайнятий іншим користувачем),
`NOT_FOUND`.

---

### `PATCH /auth/password`

**Авторизація:** обов'язкова

**Тіло:** `{ "currentPassword": string, "newPassword": string }`

Зміна пароля **завершує всі інші сесії** на всіх пристроях: `tokenVersion`
зростає, `refreshSessions` очищається. Той, хто змінює пароль, одразу отримує
нову сесію, тож із поточного пристрою не вилітає.

**`200`** → `{ "data": null }` плюс нові cookie.

**Помилки:** `BAD_REQUEST` (поточний пароль невірний), `VALIDATION_ERROR`.

---

### `GET /auth/export`

Усе, що містить акаунт, одним документом.

**Авторизація:** обов'язкова

**`200`** → `AccountExport`:

```ts
{
  exportedAt: string;  // ISO 8601
  user: User;
  habits: HabitExport[]; // Habit + program (завдання занять) + days (кожен день, у який щось сталося, з нотатками й причинами)
  journal: JournalEntry[]; // записи щоденника
  coachCards: CoachCard[]; // картки коуча
  plans: Plan[];       // опубліковані цим акаунтом
}
```

Форму кожного об'єкта задає той самий `toJSON`, що й скрізь, тож в експорт не
потрапляє нічого, чого не показують екрани самого акаунта: ні хешу пароля, ні
сесій, ні `userId`.

---

### `POST /auth/forgot-password`

Надсилає на пошту посилання для вибору нового пароля.

**Авторизація:** не потрібна · **Ліміт:** 5 на годину по IP

**Тіло:** `{ "email": string }` — нормалізується так само, як при реєстрації.

**`200`** → `{ "data": null }` — **завжди**, є такий акаунт чи ні. Інакше цей
ендпоінт став би списком зареєстрованих адрес. Лист надсилається без
очікування, щоб час відповіді теж нічого не видавав.

Посилання має вигляд `{APP_URL}/reset-password#token=…`: токен у фрагменті, а
не в query, тож він не потрапляє ні на сервер, ні в `Referer`. Діє 30 хвилин і
один раз; новий запит замінює попередній токен. У базі зберігається лише
SHA-256 токена.

**Помилки:** `VALIDATION_ERROR` (не адреса), `RATE_LIMITED`.

---

### `POST /auth/reset-password`

**Авторизація:** не потрібна · **Ліміт:** автентифікація

**Тіло:** `{ "token": string, "newPassword": string }` — пароль за тими ж
правилами, що й при реєстрації.

Встановлює новий пароль, **завершує всі інші сесії** (як і зміна пароля) і
одразу видає нову.

**`200`** → `{ "user": User }` плюс cookie сесії.

**Помилки:** `BAD_REQUEST` — токен невідомий, уже використаний або
прострочений; `VALIDATION_ERROR`.

Звичайна зміна пароля (`PATCH /auth/password`) теж анулює невикористане
посилання — інакше лист у скриньці міг би скасувати цю зміну.

---

### `DELETE /auth/account`

**Авторизація:** обов'язкова

**Тіло:** `{ "password": string }` — підтвердження паролем, щоб викрадена сесія
не могла видалити акаунт.

Видаляє користувача **і всі його звички разом із їхніми днями, нотатками, записами щоденника й картками коуча — повністю, без м'якого видалення**, а його опубліковані плани знімає з
бібліотеки (`unpublished`) і стирає з них `displayName`. Плани не видаляються
фізично: звички інших людей, взяті з них, зберігають свій `fromPlanId`.

**`200`** → `{ "data": null }`

**Помилки:** `BAD_REQUEST` (пароль невірний).

## Ендпоінти `/habits`

Усі потребують авторизації. Усі операції скоуплені за власником: чужа звичка
повертає `NOT_FOUND`.

**Модель.** Звичка зберігає не рядок на кожен день, а *правила* (що вона
просить і з якого дня), необов'язкову *програму* (завдання по заняттях),
паузи й вихідні. Журнал `HabitDay` тримає лише дні, у які щось сталося:
відмітку, кількість чи відмічені кроки. Які дні заплановані, що вони варті,
серія, відсоток і кінець програми **обчислюються при читанні**
(`services/habitTimeline.ts`) і не зберігаються, тож застарілими бути не можуть.
Деталі — у [`HABIT_MODEL_V2.md`](HABIT_MODEL_V2.md).

**«Сьогодні».** Сервер читає дні в UTC, але людина на захід від Гринвіча ще
живе вчорашнім днем, коли в UTC вже настав наступний. Ендпоінти, що рахують
стан дня (`GET /habits/daily`, `complete`, `value`, `steps`), приймають
необов'язкове `today` (`YYYY-MM-DD`) — власний «сьогодні» клієнта. Йому
вірять, лише якщо воно в межах доби від серверного; далі — це вже не часовий
пояс, і береться серверне. Без цього живий день людини називався б
«пропущеним».

### `POST /habits`

Створює звичку вручну.

**Тіло**

| Поле | Тип | Правила |
| --- | --- | --- |
| `title` | string | 1–100 символів |
| `description` | string? | до 500 символів |
| `category` | string? | до 50 символів |
| `steps` | array? | `[{ title: string }]`, до 20 кроків, назва 1–100 символів. Щоденний чекліст: стан кроку зберігається по днях |
| `startDate` | string \| Date | **не в минулому** (порівняння по днях у UTC, з добою запасу) |
| `sessions` | number? \| null | кількість занять, ціле 1–365. **Відсутнє — звичка без кінця** |
| `frequency` | object? | `{ kind: "daily" }` (за замовчуванням), `{ kind: "weekdays", days: number[] }` (1 = пн … 7 = нд, непорожній, без повторів), `{ kind: "weekly", times: 1–7 }` |
| `target` | object? | `{ value: number, unit: string }` — кількість за день: `value` > 0 і ≤ 10 000, один знак після коми, `unit` до 20 символів. Напрям береться з `type`: `build` — не менше, `quit` — не більше |
| `timeOfDay` | `"morning"` \| `"afternoon"` \| `"evening"` \| `"anytime"` | за замовчуванням `anytime` |
| `type` | `"build"` \| `"quit"` | — |
| `color` | string | непорожній |
| `icon` | string | непорожній |

Заняття програми одержують назву звички як завдання; їх можна переписати
вручну (`PATCH /habits/:id/day`).

**`201`** → `{ "habit": Habit }`

### `POST /habits/ai`

Те саме, але завдання по заняттях пише OpenAI.

**Ліміт:** 5 запитів на годину, по користувачу

**Тіло:** `title`, `startDate`, `type`, `color`, `icon`, `description?`,
`category?`, `steps?`, `frequency?`, `target?`, `timeOfDay?` — як вище, плюс
`sessions` **необов'язкове**: відсутнє, `null` або `0` означають «нехай модель
сама обере кількість занять» (у межах 21–90). Безстрокову звичку тут задати
нічим — для неї немає чого писати.

Частоту й ціль задає людина, модель лише отримує їх як дані й пише завдання
*по заняттях* («заняття 4 з 36»), а не по календарних днях.

`description` передається моделі як контекст — рівень, обмеження, мета — щоб
завдання були під людину, а не загальні. У промпті він огороджений і
позначений як слова користувача, а не інструкції.

**`201`** → `{ "habit": Habit, "aiGenerated": true }`

**Помилки:** `SERVICE_UNAVAILABLE` (OpenAI недоступний), `RATE_LIMITED`.

### `GET /habits/daily`

Головний ендпоінт щоденного екрана.

**Query:** `date` — необов'язкова, за замовчуванням сьогодні. `today` —
необов'язкова, див. вище.

Повертає звички, які мають що сказати про цю дату: вона заплановане заняття,
пауза чи вихідний — або це `weekly`-звичка в межах свого періоду (вона
показується щодня, доки тижнева ціль не досягнута, і лишається видимою після).
Кожна звичка несе `day` — цей день, уже пораховано. Тому показ одного дня не
тягне за собою решту.

**`200`**

```json
{
  "date": "2026-07-31T00:00:00.000Z",
  "habits": [
    {
      "_id": "...",
      "title": "Пити воду",
      "timeOfDay": "morning",
      "frequency": { "kind": "daily" },
      "target": { "value": 8, "unit": "склянок" },
      "sessions": 30,
      "endDate": "2026-07-30T00:00:00.000Z",
      "currentStreak": 5,
      "streakUnit": "day",
      "isCompleted": false,
      "progress": { "done": 18, "decided": 20, "percentage": 90, "sessionsTotal": 30 },
      "day": {
        "date": "2026-07-31T00:00:00.000Z",
        "state": "pending",
        "value": 3,
        "target": { "value": 8, "unit": "склянок" },
        "completedSteps": [],
        "session": { "index": 21, "total": 30, "title": "Сьома склянка до 18:00" }
      }
    }
  ]
}
```

**Щоденник у відповіді.** Поряд із `habits` є `journal` — запис щоденника цього
дня (`JournalEntry`) або `null`, щоб денний екран не робив другого запиту. Дні
несуть ще `note`, `failureReason` і `reasonPrompted`.

`day.state` — `pending`, `done`, `failed`, `missed`, `paused` або `rest`.
`missed` рахує **сервер**: минулий день, у якому нічого не відмічено; для
`weekly`-звичок день без відмітки не «пропущений», бо слот належить тижню, а
не дню. `day.week` (`{ done, target }`) є лише в `weekly`-звичок,
`day.session` — лише в програм.

**`200`** → `{ "habit": Habit }` · **Помилки:** `VALIDATION_ERROR` (id не є

### `PUT /habits/:id`

**Тіло** — непорожня підмножина полів створення. Правило «не в минулому» тут
**не діє**: наявна звичка цілком законно могла початися раніше. `sessions`
змінює довжину програми: скорочення відкидає зайві заняття, збільшення додає
заняття з назвою звички. Звичку без кінця не можна зробити програмою
(`BAD_REQUEST`), і навпаки.

`steps` при редагуванні — повний новий список. Крок, переданий з `_id`, який у
звички вже є, зберігає цей id і всі свої відмітки; невідомий `_id` не
довіряється і стає новим кроком. Відмітки видалених кроків прибираються з усіх
днів.

Перейменування звички переносить нову назву в заняття, чия назва дорівнювала
старій (так програма заповнюється за замовчуванням). Заняття, написані
вручну чи AI, не змінюються.

`frequency` чи `target` не переписують минуле: вони додають **нове правило з
датою дії «сьогодні»**, а попередні дні лишаються під правилом, за яким
жили. Правило того самого дня замінюється, а те, що нічого не змінює, не
записується. `"target": null` забирає ціль.

Зміна `startDate` переносить усе, що має дату — правила, паузи, вихідні, журнал
— на однакову кількість днів: третє заняття лишається третім.

**`200`** → `{ "habit": Habit }`

---

**`200`** → `{ "habitId": string }`

### `PATCH /habits/:id/day`

Перейменовує заняття програми. Саме заняття, а не календарний день: з
паузами й вихідними вони більше не збігаються.

**Тіло:** `{ "session": number, "title": string }` (`session` — 1–365,
`title` — 1–200 символів)

**`200`** → `{ "habit": Habit }`

**Помилки:** `BAD_REQUEST` — звичка без кінця або такого заняття немає.

---

### `PATCH /habits/:id/complete`

Виставляє статус дня **для звички без кількості**. Перераховує серію й
завершення.

**Тіло:** `{ "status": "pending" | "done" | "failed", "date"?: string, "today"?: string }`
— без `date` береться сьогодні.

`failed` — це «я цього не зробив», сказане користувачем, і воно обриває серію.
`pending` повертає день у невідмічений стан. Стану «прострочено» тут немає: він
випливає з дати і не зберігається.

Не можна відмітити день у паузі, вихідний, день, якого немає в розкладі, і —
для `weekly` — ще один день, коли тиждень уже виконано. Звичка з ціллю
відмічається через `value`, а не цим ендпоінтом.

**`200`** → `{ "habit": Habit, "day": HabitDay }`

**Помилки:** `BAD_REQUEST` — див. вище.

---

### `PATCH /habits/:id/value`

Кількість за день для звички з ціллю.

**Тіло:** `{ "date": string, "value": number, "today"?: string }` — `value`
від 0 до 10 000, один знак після коми.

`build`: день виконано, коли `value` ≥ цілі; нуль знімає запис. `quit`: день
**зірвано** одразу, як тільки `value` перевищує межу, але виконаним він стає
лише по завершенні — до опівночі межу ще можна порушити. «Чистий день» — це
`value: 0`, і його треба сказати: без цього минулий день просто пропущений.

**`200`** → `{ "habit": Habit, "day": HabitDay }`

**Помилки:** `BAD_REQUEST` — звичка не має цілі; день поза розкладом, у паузі чи
на вихідному.

---

### `PATCH /habits/:id/steps/:stepId`

Відмічає або знімає відмітку кроку **в конкретний день**. Крок — пункт
щоденного чекліста, тож його стан належить дню, а не звичці: відмічений у
понеділок у вівторок знову порожній.

**Тіло:** `{ "date": string, "today"?: string }` — день (`YYYY-MM-DD`),
обов'язковий.

Відмітка останнього кроку робить день `done`, якщо ніхто ще його не вирішив.
День, який користувач уже відмітив сам (`done` чи `failed`), не змінюється, і
зняття кроку ніколи не забирає `done` назад. Для звички з ціллю чекліст дня не
завершує: його завершує кількість.

**`200`** → `{ "stepId": string, "completed": boolean, "habit": Habit, "day": HabitDay }`

**Помилки:** `VALIDATION_ERROR` (некоректний id або немає `date`),
`BAD_REQUEST` (день поза розкладом), `NOT_FOUND` (немає такої звички або
кроку).

### Нотатка й причина зриву

Контекст дня звички: кілька слів про те, як пройшло, і — для зірваного дня —
чому. Це сировина для коуча, а не для людей: у план при публікації нічого з
цього не потрапляє.

| Ендпоінт | Тіло | Примітки |
| --- | --- | --- |
| `PATCH /habits/:id/days/:day/note` | `{ "note": string }` | до 280 символів; порожній рядок прибирає нотатку. `:day` — `YYYY-MM-DD`; день має бути в розкладі звички й не в майбутньому (з добою запасу) |
| `PATCH /habits/:id/days/:day/reason` | `{ "code": ReasonCode, "text"?: string }` або `{ "skipped": true }` | лише для дня зі станом `failed` (`400` інакше); `text` до 200 символів |

`ReasonCode` — `no_time` · `forgot` · `no_energy` · `ill` · `circumstances` ·
`didnt_want` · `other`. Закритий перелік, бо лише його можна порахувати.
`skipped` записує тільки `reasonPrompted: true` — «питали, відмовились» — щоб не
питати двічі; уже наявну причину воно не стирає.

Причина **зникає**, щойно день перестає бути `failed` — день зняли, змінили
ліміт `quit`, скоротили програму: причина зриву, якого не було, брехала б
статистиці. `reasonPrompted` лишається.

**`200`** → `{ "habit": Habit, "day": HabitDay }`

---

### Паузи

Пауза — відрізок днів, які не рахуються: вони не слоти, нічого не «з'їдають» і
не рвуть серію. Паузу не можна **почати в минулому** (з добою запасу) і не
можна скоротити заднім числом — лише закрити: «відновити» — це `to` = вчора.
Інакше будь-який зрив міг би постфактум стати паузою.

| Ендпоінт | Тіло | Примітки |
| --- | --- | --- |
| `POST /habits/:id/pauses` | `{ "from": string, "to"?: string }` | без `to` пауза відкрита. `409`, якщо перетинає іншу; `400`, якщо починається в минулому чи на вже відмічений день |
| `PATCH /habits/:id/pauses/:pauseId` | `{ "to": string }` | закрити чи пересунути кінець; не раніше вчора і не раніше початку |
| `DELETE /habits/:id/pauses/:pauseId` | — | лише пауза, що ще не почалась; інакше `400` |

**`201`/`200`** → `{ "habit": Habit }`. Кінець програми пересувається на
довжину паузи; відкрита пауза робить його невідомим (`endDate` відсутнє).

### Вихідні

Вихідний — один день, який не рахується. Лише для звичок `daily`, лише
сьогодні чи наперед, **не більше одного на тиждень (пн–нд)** і не на день, який
уже відмічено.

| Ендпоінт | Тіло | Примітки |
| --- | --- | --- |
| `POST /habits/:id/rest-days` | `{ "date": string }` | `400` — у минулому, не `daily`, уже відмічений, другий за тиждень, поза програмою |
| `DELETE /habits/:id/rest-days/:date` | — | лише сьогоднішній чи майбутній; `404`, якщо такого вихідного немає |

**`201`/`200`** → `{ "habit": Habit }`.

### `POST /habits/from-plan`

Бере план із бібліотеки й створює з нього власну звичку.

**Авторизація:** обов'язкова

**Тіло**

| Поле | Тип | Правила |
| --- | --- | --- |
| `planId` | string | ObjectId опублікованого плану |
| `startDate` | string \| Date | **не в минулому**, як і при звичайному створенні |
| `sessions` | number? | 1–365; за замовчуванням — довжина плану |
| `frequency`, `target` | object? | як при створенні; за замовчуванням — із плану |
| `color`, `icon` | string? | за замовчуванням — із плану |

Назва, опис, категорія, частина дня і всі завдання **читаються з плану**, а не
з тіла. Довжину, частоту чи ціль змінити можна, але такий клон перестає
збігатися з `contentHash` плану й **виключається з його статистики**: людина,
яка пройшла 30 занять зі взятих 90, не проходила цей план.

Окремий маршрут, а не опційний `planId` у `POST /habits`: інакше
`createHabitSchema` перетворюється на union з умовно обов'язковими полями, і тип
із `z.infer` стає непридатним. `POST /habits/ai` — той самий прецедент.

**`201`** → `{ "habit": Habit, "fromPlan": true }`

**Один прохід плану за раз.** Якщо в користувача вже є звичка з цього плану, чия
програма ще не завершилась, — `409 CONFLICT`. Дві копії кладуть одне й те саме
завдання двічі на один день, і це не два зобов'язання, а одне, показане двічі.
Коли попередній прохід завершився календарно, план можна брати знову.

**Помилки:** `VALIDATION_ERROR`, `NOT_FOUND` (плану немає або він знятий),
`CONFLICT` (цей план уже йде).

## Ендпоінти `/journal`

Усі потребують авторизації. Щоденник належить людині, а не звичці: він переживає
видалення будь-якої звички і йде разом з акаунтом. Усе в записі необов'язкове —
щоденник, що вимагає писати, перестають відкривати.

### `PUT /journal/:day`

Створює або **замінює** запис дня. `:day` — `YYYY-MM-DD`.

**Тіло:** `{ "mood"?: 1–5, "energy"?: 1–5, "text"?: string }` — `text` до 2000
символів, обрізається. Поле, якого немає в тілі, **прибирається** — так людина
забирає настрій назад. Запис без жодного поля не зберігається: порожнє тіло його
видаляє.

Писати можна за будь-який минулий день і за сьогодні (з добою запасу для того, хто
східніше від сервера); за майбутній — `400`.

**`200`** → `{ "entry": JournalEntry | null }` — `null`, коли запис порожній.

### `DELETE /journal/:day`

**`200`** → `{ "day": string }`. Дня без запису це не помилка.

### `GET /journal?from=&to=`

Записи за проміжок включно, від старих до нових. Не більше **92 днів**; `to` не
раніше за `from`. Читається агрегацією: `sanitizeFilter` перетворив би `$gte` на
порожню відповідь.

**`200`** → `{ "entries": JournalEntry[] }`

## Ендпоінти `/coach`

Усі потребують авторизації; скоупінг власника — в сервісі, чужа картка — `NOT_FOUND`.
Специфікація й причини рішень — [`AI_COACH.md`](AI_COACH.md).

**Головний принцип: числа рахує код, AI лише говорить.** Відсотки, серії, пороги
закономірностей і пропозиція «як полегшити» — чисті функції
(`services/coachInsights.ts`) з порогами й тестами; модель отримує готові факти й
формулює їх, а відповідь перевіряється: форма, довжина і числа, яких немає у фактах,
відхиляються. Нижче порогів коуч мовчить, і заглушок замість тексту немає.

**Що йде в модель:** назви звичок (нумеровані), типи, ритм, цілі, пораховані факти,
кількість причин за кодами, середні настрою й енергії. **Лише з `coachReadsNotes`:**
нотатки й текст щоденника за 14 днів, кожен до 280 символів, усього до 2000.
**Ніколи:** ім'я, прізвище, email, дата народження, будь-які id. У лог — лише вид
картки, модель, токени й час. Модель — `COACH_MODEL` (за замовчуванням `gpt-4o-mini`).

### `POST /coach/refresh`

Каже те, що «настало», і більше нічого. Клієнт викликає його при відкритті денного
екрана; фонових задач немає.

- **Тижневий огляд** — за тиждень (пн–нд), що вже скінчився, якщо є щонайменше 7
  днів історії. Один на тиждень.
- **Пропозиція полегшити** — для кожної звички, де поспіль зірвано 3 слоти
  (`failed` чи `missed`, тож ловляться й дні без жодної відмітки), якщо звичка не на
  паузі, не завершена й її правило не змінювали останній тиждень. Картка зі
  статусом `candidate`: пропозицію пораховано, **моделі не питали**. Одна на звичку
  на тиждень.
- **Інсайт** — не більше одного на добу; та сама закономірність про ту саму звичку
  не повторюється частіше, ніж раз на 30 днів.

Повторний виклик знаходить усі картки на місці й нічого не генерує. Картка
резервується до звернення до моделі, тож паралельні виклики доходять до неї один
раз. Невдала генерація — друга спроба при наступному виклику, потім відмова.

**`200`** → `{ "cards": CoachCard[] }` — лише створені цим викликом.

### `GET /coach/cards?limit&before`

Історія від нових до старих. `limit` — 1–50 (20 за замовчуванням), `before` —
курсор (`nextCursor` попередньої сторінки). Картки, що не вдалось написати, не
показуються; пропозиції `candidate` — показуються.

**`200`** → `{ "cards": CoachCard[], "nextCursor"?: string }`

### `POST /coach/cards/:id/open`

Для пропозиції `candidate`: модель пояснює її (і, для програми, переписує завдання
наступних 7 занять). Для решти — повертає картку як є, нічого не коштуючи.

**`200`** → `{ "card": CoachCard }` · **`503`** — модель недоступна; пропозиція
лишається, після другої невдачі стає `failed`.

### `POST /coach/cards/:id/apply`

Застосовує пропозицію **через ті самі сервісні функції, що й ручне редагування**:
нове правило з датою «сьогодні», минуле лишається під старим, клон плану з
бібліотеки виходить зі статистики плану так само, як і від ручної зміни.

**`200`** → `{ "card": CoachCard, "habit": Habit }`

**`409 CONFLICT`:** не пропозиція; уже застосована чи закрита; не відкрита (людина
має побачити, що зміниться); звичку відтоді змінили чи видалили.

### `POST /coach/cards/:id/dismiss`

Закриває картку. Застосована лишається застосованою. **`200`** → `{ "card": CoachCard }`

### `POST /coach/cards/:id/feedback`

**Тіло:** `{ "helpful": boolean }` — можна передумати. **`200`** → `{ "card": CoachCard }`

## Ендпоінти `/plans`

Публічна бібліотека планів. Повний опис ухвалених рішень і їхніх причин — у
[`EXPLORE_PLAN_LIBRARY.md`](EXPLORE_PLAN_LIBRARY.md).

**Читання не потребує сесії, дії потребують.** `GET /plans` і `GET /plans/:id`
відповідають будь-кому, але **знають** про сесію, якщо вона є: без неї
`days` обрізаються до перших трьох і додається `daysTruncated: true`. Прострочена
або підроблена cookie тут не помилка — читач просто вважається гостем.

Плани зі статусом `unpublished` і `removed` для всіх, крім `GET /plans/mine`,
не існують: `NOT_FOUND`.

### `GET /plans`

**Query**

| Поле | Тип | Правила |
| --- | --- | --- |
| `category` | string? | одна з переліку категорій; інше значення — `VALIDATION_ERROR` |
| `language` | string? | дволітерний код ISO 639-1 |
| `section` | `official` \| `proven` \| `new` | без нього — усі опубліковані |
| `cursor` | string? | непрозорий; береться з `nextCursor` попередньої сторінки |
| `limit` | number? | 1–50, за замовчуванням 20 |

Секції — це редакційні полиці, а не фільтри: `official` — засіяні проєктом,
`proven` — із значком або від 10 взять, `new` — решта. Сортування: офіційні й
нові за `createdAt` спаданням, «пройдені» — за відсотком проходження, далі за
кількістю взять.

**`200`** → `{ "plans": PlanSummary[], "nextCursor"?: string }`

`nextCursor` відсутній, коли сторінка остання. **Список ніколи не містить
`days`** — картка їх не показує, а 365 рядків на кожен із двадцяти планів возити
нема за чим.

---

### `GET /plans/:id`

**`200`** → `{ "plan": Plan }`

Із сесією — весь зміст. Без сесії — перші 3 дні та `daysTruncated: true`.

**Помилки:** `VALIDATION_ERROR` (id не є ObjectId), `NOT_FOUND`.

---

### `POST /plans`

Публікує звичку як план.

**Авторизація:** обов'язкова · **Ліміт:** 5 на добу, по користувачу

**Тіло:** `{ "habitId": string, "category": PlanCategory, "displayName"?: string }`

**Зміст не приймається від клієнта взагалі.** Назва, опис, довжина, частота,
ціль, частина дня, кольори й завдання всіх занять читаються сервером зі звички
— інакше можна опублікувати одне, а показати собі інше, і `contentHash`
перестає щось означати. Публікується лише **програма**: безстрокова звичка не
має завдань, які віддати бібліотеці (`BAD_REQUEST`).

`contentHash` для щоденного плану без цілі лишається таким, яким був до появи
частоти, — до біта, тож хеші вже опублікованих планів чинні без перерахунку.
Для решти він охоплює частоту й ціль, і рахується за правилом, **чинним зараз**:
змінений посеред шляху ритм — це відхилення від маршруту, що його описує план.

`displayName` (до 30 символів) — єдине, чим план може бути підписаний. Без нього
план анонімний; ім'я, прізвище, email і статистика автора не показуються ніколи.
Передане ім'я також зберігається в акаунті, щоб форма могла підставити його
наступного разу, але підписом воно стає лише тоді, коли надіслане явно.

Перед записом план **синхронно** проходить перевірку моделлю, яка одним викликом
повертає і мову, і вердикт безпеки. Гейт **fail closed**: недоступний OpenAI —
`503`, а не тихий пропуск. Публікація не термінова, на відміну від генерації
звички, а неперевірений план у публічній бібліотеці — саме той результат, заради
якого варто відмовити.

**`201`** → `{ "plan": Plan }`

**Помилки:** `VALIDATION_ERROR`, `BAD_REQUEST` (звичка без кінця), `NOT_FOUND`
(чужа звичка), `CONFLICT` (цю звичку вже опубліковано), `CONTENT_REJECTED` (вердикт модерації, `message` — пояснення
для автора), `SERVICE_UNAVAILABLE`, `RATE_LIMITED`.

---

### `PATCH /plans/:id`

**Авторизація:** обов'язкова · тільки автор

**Тіло** — непорожня підмножина: `title`, `description`, `category`.

Поденний зміст не редагується. Це ламало б одразу дві домовленості: знімок у
людей, які вже йдуть за планом, і збіг із джерелом, на якому тримається значок
«пройдено». Потрібні інші дні — публікується окремий план.

**`200`** → `{ "plan": Plan }` · **Помилки:** `NOT_FOUND` (чужий або знятий).

---

### `DELETE /plans/:id`

М'яке зняття: `status` стає `unpublished`. Жорстке видалення обірвало б
`fromPlanId` на кожній узятій звичці й стерло б слід для модерації.

Звичка-джерело втрачає `publishedPlanId` і може бути опублікована знову —
новим планом. План, знятий модератором (`removed`), так не звільняє звичку.

**`200`** → `{ "plan": Plan }` · **Помилки:** `NOT_FOUND`.

---

### `GET /plans/mine`

Приватний кабінет автора: власні плани, включно зі знятими, найновіші першими.

Зареєстрований **строго перед `GET /plans/:id`**, інакше `mine` розбирався б як
ObjectId і маршрут відповідав би `400` — той самий випадок, що з
`/habits/daily`.

Відкриття цієї сторінки — другий лінивий тригер дозрівання значка «пройдено»:
перший спрацьовує на відмітці дня і ніколи не спрацює в того, хто покинув звичку
на 85-му дні.

**`200`** → `{ "plans": PlanSummary[] }`

---

### `POST /plans/:id/report`

Скарга на план. Одна відкрита скарга на людину й план: друга — та сама людина з
тим самим, і черга від неї лише росте.

**Тіло:** `{ "reason": "dangerous" | "spam" | "offensive" | "nonsense" | "other",
"comment"?: string }` (`comment` до 500 символів)

**`201`** → `{ "reported": true }`

Про саму скаргу назад не повертається нічого. Черга розбирається скриптами
`npm --prefix server run moderation:queue` і `moderation:remove -- <planId>`;
інтерфейсу модерації в SPA немає.

## Форми даних

Канонічні визначення — у [`shared/src/`](../shared/src), звідти їх імпортують
обидва пакети.

### `User`

```ts
{
  _id: string;
  name: string;
  surname: string;
  birthday: string;   // ISO 8601
  gender: "male" | "female";
  email: string;
  avatar?: string;    // data URI, поки користувач не вибрав — відсутній
  role?: "user" | "admin";
  displayName?: string;  // ім'я для підпису планів; відсутнє = анонім
  preferences: {
    askFailureReason: boolean;   // за замовчуванням true
    coachLanguage?: string;      // ISO 639-1; відсутнє = «авто» (мова назв звичок)
    coachReadsNotes: boolean;    // за замовчуванням false
  };
  createdAt: string;
  updatedAt: string;
}
```

`password`, `tokenVersion` і `refreshSessions` не потрапляють у відповідь
ніколи — їх зрізає `toJSON` у моделі.

`role` не секрет і лишається у відповіді, але **не приймається жодною схемою**:
ні реєстрація, ні `PATCH /auth/profile` його не містять, тож захист структурний.
У документів, створених до появи поля, його немає — `role === 'admin'` для них
`false`, що і є безпечним прочитанням.

### `Habit`

```ts
{
  _id: string;
  title: string;
  description?: string;
  category?: string;
  steps?: { _id: string; title: string }[];
  startDate: string;            // ISO 8601, північ UTC
  type: "build" | "quit";
  color: string;
  icon: string;
  timeOfDay: "morning" | "afternoon" | "evening" | "anytime";
  rules: { effectiveFrom: string; frequency: Frequency; target?: Target }[];
  frequency: Frequency;         // правило, чинне сьогодні
  target?: Target;
  sessions?: number;            // довжина програми; відсутнє = без кінця
  endDate?: string;             // останній день програми; прогноз, поки не минув
  pauses: { _id: string; from: string; to?: string }[];
  restDays: string[];
  currentStreak: number;
  streakUnit: "day" | "week";   // що рахує currentStreak
  isCompleted: boolean;         // усі заняття програми позаду; для безстрокової завжди false
  progress: { done: number; decided: number; percentage: number; sessionsTotal?: number };
  fromPlanId?: string;          // якщо звичку взято з бібліотеки
  publishedPlanId?: string;     // якщо з неї опубліковано план
  createdAt: string;
  updatedAt: string;
}

type Frequency =
  | { kind: "daily" }
  | { kind: "weekdays"; days: number[] }   // 1 = пн … 7 = нд
  | { kind: "weekly"; times: number };     // 1–7 на тиждень (пн–нд)

type Target = { value: number; unit: string };
```

`currentStreak`, `isCompleted`, `progress` і `endDate` **рахуються при
читанні**, а не беруться зі збереженого. Відсоток — виконані слоти до слотів,
які вже минули: майбутнє в знаменнику показувало б 11% на десятий день ідеальної
програми.

`userId`, `schemaVersion`, `program` (замість неї — `sessions`) і старі
`dailyCompletions`/`duration` **не потрапляють у відповідь**. Старі поля
залишаються в базі нетронутими, щоб попередню версію можна було відкотити;
окрема зміна прибере їх після перевірки в production.

### `HabitDay`

Один день звички, пораховано сервером.

```ts
{
  date: string;                 // ISO 8601, північ UTC
  state: "pending" | "done" | "failed" | "missed" | "paused" | "rest";
  value?: number;               // кількість, для звичок із ціллю
  target?: Target;              // ціль, чинна цього дня
  completedSteps: string[];     // id кроків, відмічених цього дня
  session?: { index: number; total: number; title: string };  // програми
  week?: { done: number; target: number };                    // weekly
  note?: string;                                              // до 280 символів
  failureReason?: { code: ReasonCode; text?: string };         // лише для failed
  reasonPrompted?: boolean;                                   // питання вже ставили
}
```

### `JournalEntry`

```ts
{
  _id: string;
  day: string;      // ISO 8601, північ UTC
  mood?: number;    // 1–5
  energy?: number;  // 1–5
  text?: string;    // до 2000 символів
}
```

### `CoachCard`

```ts
{
  _id: string;
  kind: "weekly_review" | "recalibration" | "insight";
  key: string;                 // тиждень (понеділок), «звичка:тиждень» або день
  habitId?: string;
  status: "candidate" | "ready" | "failed" | "dismissed" | "applied";
  facts: object;               // пораховане кодом; те, з чого написано текст
  proposal?: {                 // лише для пропозицій
    habitTitle: string;
    from: { frequency: Frequency; target?: Target };
    to:   { frequency: Frequency; target?: Target };
    rewrite?: { fromSession: number; current: string[]; proposed?: string[] };
  };
  content?: { title: string; body: string; win?: string; tip?: string };
  language: string;            // ISO 639-1, якою написано
  feedback?: "helpful" | "not_helpful";
  createdAt: string;
  readyAt?: string;
}
```

`userId`, вартість (`usage`), кількість спроб і відбиток закономірності (`fingerprint`,
що називає id) у відповідь не потрапляють ніколи.

### `HabitSummary`

Те, що повертає `GET /habits/daily`: усе з `Habit` плюс `day` (`HabitDay`).

### `HabitExport`

Те, що віддає експорт: `Habit` плюс `program` (`{ title }[]`, завдання кожного
заняття) і `days` — кожен день, у який щось сталося
(`{ day, status?, value?, completedSteps }`).

### `Plan`

```ts
{
  _id: string;
  title: string;
  description: string;
  category: PlanCategory;  // health | fitness | mind | learning | productivity
                           // | money | sleep | nutrition | digital | social
                           // | creativity | other
  language: string;        // ISO 639-1, визначається при публікації
  type: "build" | "quit";
  duration: number;        // кількість занять; дорівнює days.length
  frequency: Frequency;    // плани до появи частоти читаються як daily
  target?: Target;
  timeOfDay: "morning" | "afternoon" | "evening" | "anytime";
  color: string;
  icon: string;
  days: { dayTitle: string }[];  // завдання по заняттях; повністю або перші 3 — залежно від сесії
  daysTruncated?: true;          // присутнє лише в тизері
  author: { displayName?: string };  // без імені = анонім
  proven: boolean;         // автор пройшов саме цей розклад
  provenAt?: string;
  official: boolean;       // засіяно проєктом; окремий значок, не змішується
  status: "published" | "unpublished" | "removed";
  cloneCount: number;      // скільки людей узяли (лише перші взяття)
  completionRate?: number; // 0–100; відсутнє, поки взять менше 10
  createdAt: string;
  updatedAt: string;
}
```

`author.userId`, `sourceHabitId`, `contentHash`, `moderation` і
`completedCloneCount` **не потрапляють у відповідь ніколи** — їх зрізає `toJSON`
у моделі, за тим самим принципом, що й у `User` та `Habit`.

`completionRate` рахується там же і з'являється **лише від 10 взять**: нижче
цього числа він дорівнював би 100% або 0% і описував би вибірку, а не план. Разом
із ним зрізається `completedCloneCount` — інакше приховане співвідношення просто
ділиться.

### `PlanSummary`

Те, що повертають списки: усе з `Plan`, крім `days` і `daysTruncated`.

### Дати

Усі дати нормалізовані до **півночі UTC**. Інакше «сьогодні» залежало б від
часового поясу процесу і той самий день міг би збігатися або не збігатися
залежно від того, де запущено сервер.

**Клієнт надсилає день як `YYYY-MM-DD`, а не як повний ISO-момент.** Календарний
день — це локальний день користувача, той, що написаний на клітинці, яку він
натиснув. Локальна північ, пропущена через `toISOString()`, — це попередній день
за UTC скрізь на схід від Гринвіча, тож повний момент означав інший день, ніж
той, що на екрані. Голий ключ дня однозначний: сервер парсить його як північ
UTC, що збігається з тим, як зберігається розклад.

У зворотний бік мітки з відповіді — це вже північ UTC, і читати їх треба
UTC-акцесорами. Локальні геттери зсувають їх на добу на захід від Гринвіча.

Перевірка «дата не в минулому» при створенні має допуск в один день: локальний
день клієнта може відставати від UTC-дня сервера (користувач у UTC−5 о 20:00 ще
на 7-му, коли сервер уже на 8-му).
